## Proposed new file structure

1. **Scope and flows:** M1 boundary, requirement IDs, user journeys and unresolved runtime facts. Include a clear “not implemented” label for design specimens.
2. **Foundations and components:** shadcn-compatible tokens, light/dark modes, typography, focus, buttons, fields, conversation messages, task states and approval cards. Reuse maintained components before designing custom equivalents.
3. **M1 desktop:** only the screens/states below, with links to the owning issues and source requirements.
4. **Later product explorations:** optional separate page for agreed General Chat documents/research and Coding workflows. No requirement to design all later features before M1. Unagreed legacy features stay out.

## When the broader features are added

Use the design triggers below whenever work is selected or a milestone is planned. They are durable development checkpoints, not dates or permission to start every future design now.

All accepted product requirements remain in the product specification. M1 is the connected foundation and has existing GitHub tasks; it is not the full build. Complete and practically qualify M1 before declaring that foundation accepted. Later design work can be prepared in bounded increments when authorised, but a design specimen does not establish implementation readiness.

Proposed later capability groups are (a) web research and document/artifact workflows, including spreadsheets with formulas/charts and presentations, (b) Coding with isolated copies, reviewed Apply changes and app preview, and (c) integrations, personal/project memory and expanded deployment/platform support. Some capabilities may be prerequisites for others. The owner has not yet agreed the sequence, milestone numbering, scope sizes or dates for these groups; they must not be treated as an approved delivery schedule or expanded M1. Before each capability is built, cross-reference current Deep Agents docs/skills, qualify maintained reuse options, agree any bespoke component boundary, design its states and define practical acceptance. First meaningful live behaviour must pass before affected unit tests, under the existing C1–C4 and resource rules.

### DT-11 When a CLI or mobile client is selected

Do not add mobile navigation or terminal controls to the M1 screens merely because the service can support another client.

For a CLI, produce an interaction/command specification covering connection/authentication, prompts and streamed output, task/history identity, approvals/denials, Stop, Resume and reconnect/error outcomes. Figma terminal mock-ups are optional; a terminal chat/control client does not add an interactive execution shell or automatic non-interactive approval.

For mobile, agree native versus mobile-web scope and secure connection approach before designing connection/authentication, task/conversation state, approval decisions, Stop/Resume, service unavailable, network change and app background/foreground. Show that the service host must remain available; keep provider keys service-side. Do not imply offline agent execution, automatic cross-device synchronisation, mobile push notifications or a selected mobile SDK from the existing desktop/framework designs. Those require their own scope/qualification where requested.

Both clients must reflect the same service-owned task/run identities, allowance/increase decisions and aggregate concurrency limits. The design task records supported SDK/server reuse versus actual gaps, exact interaction/frame links and meaningful independent critique; required designs and unresolved material decisions gate only dependent client work. Re-run this trigger under DT-10 if adding a client changes an existing user-facing flow.
